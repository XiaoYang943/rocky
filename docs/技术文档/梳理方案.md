# Rocky 架构与技术实现梳理方案

术语用法见[术语表](术语.md)；本篇保留英文底层术语，中文用于解释。

方案版本：v1。用户已要求先完成全部 P0；七篇 P0 正文已按本方案展开，第 3 轮按用户反馈补充术语表并统一英文用词。交付、自检和人工内容验收状态见[rocky／技术文档-001](任务/001-Rocky架构与技术实现梳理.md)第 3 轮，第 2 轮结果保留为历史。P1/P2 保留后续规划，正文的完成不等于功能运行验证完成。

## 目标与分析原则

面向缺少 OSG、osgEarth、VSG 背景的开发者，使读者能够回答：Rocky 负责什么、怎样调用已有接口、数据怎样进入 GPU、遇到加载失败应查哪一层，以及哪些能力需要依赖库或额外研发。

每项能力沿“公开入口 → 实现 → 直接调用方 → 相关示例或测试 → 错误与资源释放”展开。涉及 GPU、坐标、地形或异步任务时再向下一层追踪，不逐行翻译全库，也不以类名清单代替机制解释。

沿用 GeoStudio 当前验证目标：优先发现和说明现成接口，允许后续通过依赖选项及少量连接代码验证；涉及新增格式解析、调度器、样式引擎或第三方兼容补丁的工作，列为独立后续事项。

## P0：建立知识基础与四条核心技术路线

### 基础知识

目标：帮助读者理解后续每个术语在系统中的位置。

主要内容：

1. Scene Graph 是什么：Node、父子关系、变换、Bounding Volume；数据模型中的“Layer”与渲染图中的“Node”有什么关系。
2. 一帧的工作：事件、更新、Culling、记录命令、提交、显示；CPU 数据、GPU 资源和屏幕图像的区别。
3. OSG、osgEarth、VSG、Rocky 的职责。分别说明 `osgEarth → OSG → OpenGL` 与 `Rocky → VSG → Vulkan` 两组体系；概念相似不表示接口或资源格式直接兼容。
4. GDAL/OGR 与 PROJ 的职责：读取格式、SRS、投影转换和最终绘制分别由谁负责。
5. Tile Pyramid、LOD、Culling、Parent Fallback、按需加载为什么存在；原始 TIFF 通过运行时请求生成 Tile 与 预生成 Tile 有什么区别。
6. Geodetic Coordinates、Projected Coordinates、ECEF、局部 ENU、模型坐标的直观关系；角度、弧度和米的区别。
7. ECS 的 Entity、Component、System，及其与 Scene Graph 协同的意义。
8. Qt、ImGui、React/Tauri 的定位。说明 Qt 是可选集成，Render Window 和前端 UI 不是同一层。

图示：技术职责图、单帧流程图、地理数据到画面的总流程图。OSG/osgEarth 只补足理解所需背景，不扩展为它们的全库源码分析。

### 总体架构

重点入口：`Application`、`DisplayManager`、`Map`、`Layer`、`MapNode`、`VSGContext`、`Context`、`TerrainNode`、`Registry`、`ECSNode`。

需要回答：

- `Map` 保存哪些地理数据和 Layer 状态，`MapNode` 怎样把它们组织为 VSG 场景，为什么两者分开。
- `Application` 默认创建什么，哪些对象可以由宿主自己管理；自定义 Frame Loop 的责任是什么。
- `Context`、`IOOptions` 和 `VSGContext` 分别提供哪些上下文，谁持有和释放资源。
- 影像/高程路线、普通矢量 Geometry 路线、普通模型 Node 路线在哪里汇合。
- 配置反序列化、Layer 创建、打开、更新、关闭、移除的基本顺序和失败传播。
- Layer 是加载数据的入口，ECS/场景 Node 是组织可绘制对象的入口，二者如何组合。

交付：模块职责表、对象关系图、应用初始化与单帧时序图、三条数据链路总图。源码目录按职责介绍，避免复制整棵文件树。

### 坐标系统

用户指定入口：`SRS`。补充 `SRSOperation`、`GeoPoint`、`GeoExtent`、`Ellipsoid`、`Units`、`GeoTransform`、`Profile`。

梳理内容：

1. `SRS` 的定义方式：内置常量、EPSG、WKT、PROJ 定义；有效性、等价性及水平/垂直差异。
2. `SRS::to` 到 PROJ 操作的创建、正向/逆向变换、错误返回和 Thread-Local 对象 Cache。
3. 经度纬度顺序、Axis Order 规范化和坐标单位在这个提交中的实际处理，避免直接照抄 EPSG Metadata 或 README 的简述。
4. 数据 SRS、Profile、地图显示 Profile、World Coordinates 的区别；球面 View 与平面 View 的关系。
5. WGS84、Web Mercator、ECEF、ENU 的转换；矩阵和双精度在地球尺度中的作用。
6. 高程是椭球高还是其他 Vertical Datum，哪些转换依赖 PROJ Grid；缺失数据时的边界。
7. 跨 Antimeridian、极区、Bounds 变换、地理 CRS 绑定关系的相关测试入口。

交付：一张坐标链路图、单位与 Axis Order 表、典型错误对照表，以及最小调用方式的说明。不会把投影转换描述成坐标纠偏或地图服务的偏移修正。

### Layer 与 Tile

补充该章节的原因：`TMSImageLayer`、`GDALImageLayer` 和 `TMSElevationLayer` 共享的流程不能在三个章节重复解释。

重点入口：`Layer`、`VisibleLayer`、`TileLayer`、`ImageLayer`、`ElevationLayer`、`Profile`、`TileKey`、`GeoImage`、`TerrainTileModelFactory`。

梳理内容：Layer 层次和生命周期；Tile 坐标到空间范围；XYZ/TMS 行号方向；最小/最大 Level；覆盖范围；源 Profile 与请求 Profile 不同的处理；Parent Fallback、Cache 及无数据；增删、Visibility、Opacity 与更新通知。明确方法返回图像、高程还是可绘制 Node，避免把所有数据源统称为“渲染 Layer”。

交付：继承关系图、通用请求流程图、TileKey/Profile 参数说明；为栅格和地形章节提供唯一的通用机制说明。

### 栅格

用户指定入口：`TMSImageLayer`、`GDALImageLayer`。补充 `TMS::Driver`、`GDAL_detail::Driver`、`ImageLayer`、`Image`、`GeoImage`；`MBTilesImageLayer` 作为能力边界及 P1 构建关联入口。

对 `TMSImageLayer`：

- 标准 TMS 服务 Metadata 与通用 XYZ 模板分别如何打开；本地文件路径和网络 URI 经过哪些读取接口。
- `profile`、`uri`、`invertY`、Level 和范围如何决定实际请求。
- 请求、解码、地理范围、缺 Tile 和错误返回如何连接到通用 ImageLayer。
- 多 Layer Color Compositing、Opacity、Layer 顺序在哪里实现。

对 `GDALImageLayer`：

- Dataset 打开、驱动选择、地理变换、源 SRS、Band 和 Color Interpretation 的读取过程。
- 按 TileKey 生成局部影像时，怎样选择源窗口、Resampling、Reprojection 和利用 Overview；各项须以 GDAL.cpp 实际代码为准。
- RGB/RGBA、Gray、Palette、Alpha、NoData 的转换及不支持组合。
- Thread-Local GDAL 驱动/Dataset Handle 的持有和释放，为什么不能简单假定一个 Handle 在所有线程共享。
- GeoTIFF、COG、VRT、WMS/WMTS 等能力由哪些驱动和构建条件决定；不把 GDAL 格式总表直接等同于 Rocky 本机支持清单。

交付：TMS 与 GDAL 两张数据链路图、参数对照表、原始影像/切片影像选择表、失败排查表。

### 三维地形

用户指定入口：`TMSElevationLayer`。必须补充 `GDALElevationLayer`、`ElevationLayer`、`ElevationSampler`、`Heightfield`、`TerrainTileModelFactory`，以及 `vsg/terrain` 中的 Node、工厂、Pager、GeometryPool 和状态。

按两部分讲解：

1. 高程数据源：单通道高程、Terrain-RGB、Terrarium 的数据表示和解码位置；`TMSElevationLayer` 何时返回编码图像；`GDALElevationLayer` 如何从本地 DEM 提取高程；范围、NoData、单位及多高程层的处理。
2. 地形生成与显示：Tile Mesh 如何建立，高程如何作用到表面，影像怎样贴附；Subdivision、父子交接、边缘/Skirt、Bounding Volume 和 Visibility；CPU 数据准备、GPU 资源 Compile和场景合并之间的关系。

同时解释地形 Intersection 与源数据高程采样的差异，及矢量/模型 Clamping 为何可能受采样或当前 Resident Terrain 影响。基础性能机制在本章说明，不提前开展压力测试。

交付：数据源与渲染器分工图、Tile 加载/Refinement 时序、编码对照表、高程查询两条路线。单列 quantized-mesh 等格式的支持边界，不把“能读高程 Tile”写成“支持全部三维地形协议”。

### 矢量

用户指定入口：`GDALFeatureSource`。必须补充 `FeatureSource`、`Feature`、`Geometry`、`FeatureBuilder`、ECS 点/线/面 Component、样式和相应渲染系统。

读取与绘制分开梳理：

- `uri`、`ogrDriver`、`layerName`、`openOptions`、外部 OGR layer handle 的打开方式和生命周期。
- Metadata、Feature 属性、Geometry、SRS 如何转换为 Rocky 对象；Iterator、分块读取、异常和关闭行为。
- 点、线、Multipart、多边形、Hole 进入不同 Geometry Component 的过程；坐标变换、Localization、曲面 Subdivision、面 Triangulation 和 Clamping 的责任位置。
- `FeatureBuilder` 是 Geometry 构建工具，不能把它等同于完整制图样式引擎；颜色函数、线宽、面样式等按实际接口说明。
- 小体量 GeoJSON/SHP/GPKG 的公开接入路线；MVT 和 MBTiles 的读取能力依赖 GDAL 驱动，是否具有多 Level 调度、标签、style.json 另作判断。
- 读取、显示、Picking、修改和写回是不同能力；`GDALFeatureSource` 读取链路不自动提供编辑器。

已有 README 或设计稿与头文件不一致时，正文按固定提交的真实定义和调用点核实，并显式指出差异，不继续传播失效示例。

交付：OGR 到 ECS 再到 VSG 的流程图；三类 Geometry 构建说明；属性/样式/Picking 职责表；小体量矢量与完整 Tile 地图的能力区分。

## P1：运行机制、集成条件与可验证能力

### 数据访问与任务调度

分析 `URI`、`IOOptions`、`Context`、Cache 设施、`Threading`/weejobs、`FutureNode`、`VSGContext` 和地形 Pager 的连接。解释文件/HTTP、相对路径、资源目录、数据解码、Cache Key 与失效、取消、任务优先级、加载合并和 GPU 对象释放。

交付重点是线程/阶段所有权表和失败传播时序。区分通用 Cache 设施、实际启用的 Cache 路径和磁盘持久 Cache，避免把类存在写成全链路已开启。

### 场景与交互

分析 `NodeLayer`、`GeoTransform`、`EntityNode`、`Registry`、`ECSNode`、`MapManipulator`、`Viewpoint`、`View`、`ECSIntersector`、Camera 和窗口。

说明普通 VSG 模型 Node 如何定位到地球；经纬度、高程、局部矩阵和模型轴向之间的关系；Camera 飞行、地形 Intersection、Entity Picking、多 View 与 Visibility；显示与交互对象的生命周期。3D Tiles、OSGB、点云的实际读取由外部适配承担时，准确指出责任和版本条件。

### 工程集成

建立“CMake 开关 → 所需库 → 生成能力宏 → 运行资源 → 可验证功能”的对应表。覆盖 GDAL、PROJ、VSG、vsgXchange、CURL/HTTPLIB、SQLite/Zlib、ImGui、Qt、Slughorn 等。

构建与运行说明按仓库 AGENTS 的现有脚本核实；区分官方构建要求与 GeoStudio Demo 的既有依赖装配，不把一个工程的成功直接外推到另一个工程。

宿主方案以 Rocky 公开窗口/View/Frame Loop 入口解释独立窗口、Qt、React/Tauri 的接入职责。涉及新增宿主代码或切换 Demo 源码消费位置时另立实施范围。

### 能力矩阵与验证

每个能力保留以下字段：数据类型、入口、底层依赖、编译条件、输入形式、读取能力、绘制能力、样式/交互、现成示例、本机验证结果、缺口和下一步。

优先覆盖原始影像 TIFF、DEM TIFF、XYZ/TMS、Terrain-RGB/Terrarium、GeoJSON/SHP/GPKG、MVT、矢量/栅格 MBTiles、普通三维模型。另列 3D Tiles、quantized-mesh、OSGB、LAS/LAZ/COPC 的外部路线或未支持边界。

验证采用分层证据：

1. 源码/API 存在。
2. 当前构建已启用。
3. 数据成功读取。
4. 有正确的 GPU 画面。
5. 范围、Layer、缩放、生命周期或交互正确。

只能达到前一层时停在真实结果，不填写后续层“通过”。现有 Demo 的结果引用其主任务和产物身份，新 checkout 的独立结果单独记录。

## 每个模块的交付深度

模块 README 在公共模块模板基础上增加以下内容，短模块可合并相邻章节：

1. 用户问题与术语：先讲解决什么问题，再引入类和函数。
2. 职责及依赖：谁读取、谁变换、谁调度、谁绘制。
3. 公开接口：输入、输出、重要参数、必要调用顺序和构建条件。
4. 类型与关系图：只画理解流程需要的主要对象。
5. 核心调用链：从应用调用到实际实现和结果返回。
6. 算法/技术方案：Resampling、解码、Geometry 构建、LOD 或变换的具体实现位置及条件。
7. 生命周期与失败：Handle、线程、取消、释放、空结果和错误传播。
8. 接入说明：优先使用库内已有示例；片段注明是否实际编译验证。
9. 能力边界：已有、需启用依赖、需少量连接、需研发、未知待验证。
10. 验证入口及源码证据：固定 commit、路径、稳定符号、必要行段；链接测试和示例，但不冒充执行结果。

同一个机制只保留一份权威说明，例如 TileKey 规则放在 Layer 与 Tile，高程 RGB 解码放在三维地形，其他章节引用。

## 验证与交付标准

文档完成的标准：

- 固定源码身份；重要结论能够定位到定义、实现、调用方或已有测试。
- 概念和实现分开，公开支持、构建可用、本机显示和人工验收分开。
- 四个指定目录及类均有完整说明，不以待办列表或类注释替代正文。
- 至少能沿栅格、地形、矢量三条路线解释从数据到画面的过程。
- 关键机制有关系图/流程图，参数表包含单位、默认行为和失败边界。
- 本地链接、目录导航、源码入口、无具体日历日期规则和本轮差异通过检查。
- 没有新增底层功能、修改第三方实现或切换客户端/Demo 的消费版本。

源码研究本身不要求先重建整个工程。对代码片段或运行行为作“已验证”声明时，必须记录真实构建/运行结果；若未执行则保留可操作的验证步骤与原因。
